# Recon 05: dev site on Azure Static Web Apps (Free plan)

Asked 2026-11-17 by the orchestrator. Answered by the recon agent from Microsoft Learn pages (page `updated_at` dates in brackets). Untrusted content: none reported. Questions 7 to 12 (Cloudflare Pages option) are answered separately in recon/06.

1. **Custom domain on a preview, branch or named environment: not supported on any plan.** Learn: "Custom domains do not work with preview environments." Branch environments and named environments (`deployment_environment`) are preview environments with a generated `*.azurestaticapps.net` URL. `dev.jonwitherspoon.com` therefore needs a SECOND Static Web App resource whose production branch is `dev`. Confidence: high. [Preview environments 2026-02-25; Custom domains 2026-01-23; Branch environments 2026-03-25]
2. **Free plan limits** (Quotas 2026-09-28): 10 apps per subscription; 2 custom domains per app (apex plus www fits; dev app needs 1); 3 preview environments per app; 500 MB storage (250 MB per environment); 100 GB bandwidth per month, per subscription (two Free apps share it), no overage (a site over quota is not served). No per-app fee is listed, so a second Free app costs nothing.
3. **Actions pattern:** two SWA resources, two secrets (suggested names `AZURE_STATIC_WEB_APPS_API_TOKEN_PROD` and `..._DEV`), one workflow with two jobs gated by `github.ref` (`refs/heads/main`, `refs/heads/dev`); triggers push to main and dev plus pull_request to main. Pull-request preview and the `action: close` job stay on the PROD token only. Set `production_branch: main` on the prod job and `production_branch: dev` on the dev job. Do NOT use `deployment_environment` for dev (it makes a preview environment, which has no custom domain). Behaviour when a token's app has a different production branch is not documented (low confidence): set `production_branch` explicitly and test. Confidence: high for input behaviour, medium for the pattern. [Build configuration 2026-09-28; action.yml v1]
4. **Noindex:** nothing in the docs says preview environments get noindex automatically (medium confidence). Use `globalHeaders` in a dev-only `staticwebapp.config.json` generated into `dist` by the dev job: `{"globalHeaders": {"X-Robots-Tag": "noindex, nofollow"}}`. File must be in the root of the build output, under 20 KB. Also add `robots.txt` and a meta noindex for dev; do not combine `Disallow: /` with noindex (a blocked crawler cannot see the noindex). [Configure SWA 2026-03-25]
5. **Cloudflare DNS for a subdomain:** `CNAME dev` to the dev app's default `*.azurestaticapps.net` hostname. Subdomains validate by CNAME (no TXT needed; apex uses TXT). Keep it DNS only (grey cloud): community reports say validation fails when proxied, and certificate renewal needs the name to resolve to the app publicly. Cloudflare guidance is community-only (medium confidence). [Custom domain external providers 2026-01-23]
6. **Restricting access on Free:** password protection, IP allow-lists and private endpoints are Standard-only. Free alternative: built-in authentication (all plans; GitHub and Entra pre-configured) with a route rule requiring a custom role granted by invitation (up to 25 invitations), plus a 401 redirect to `/.auth/login/github`. The built-in `authenticated` role admits ANY GitHub or Microsoft account, so a custom role is required. Documented pattern, not run here (medium-high). Cloudflare Access would need proxied DNS, which conflicts with the DNS-only setup (not checked). [Password protection 2026-01-23; Authenticate and authorize 2026-01-23]

Overall recommendation from Recon: two Free SWA resources, two tokens, two jobs; dev job uses `production_branch: dev`, a generated config with `X-Robots-Tag: noindex, nofollow`, and optionally the role-gated route rule.
